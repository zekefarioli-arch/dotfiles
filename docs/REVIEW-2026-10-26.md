# Review of the dotfiles, 2026-10-26

Read-only review of the scripts and configs on the Ryzen 9 desktop (Ubuntu 26.04, `sh` is dash).
Every finding below was reproduced headlessly: fake binaries first in `PATH`, temporary
directories, a private Xvfb display for `xset`; nothing touched the live X session, no stow, no sudo,
no ssh. The scripts used are in the session scratchpad (`agy-tests.sh`, `misc-tests.sh`, `py-tests.py`).
The test suite (`python3 -m unittest discover -s tests`) passes: 108 tests, nothing skipped.

Counts: 0 high, 4 medium, 9 low, plus a list of document/code disagreements.

## Medium

### M1. `agy()` also rewrites the headless calls made from Claude Code sessions
`bash/.bashrc.d/agy.sh:42-62`, `docs/DECISIONS.md:9-21`, `claude/.claude/skills/gemini/SKILL.md:33-34`.
The decision says "scripts and the `gemini` skill call the real binary". They do not when the shell that
runs them has loaded `~/.bashrc.d`: Claude Code's Bash tool initialises its shell from the user's
profile, so inside every session `agy` is the function (`type -t agy` prints `function`). Without a
TTY the function takes the headless branch and prepends `--model gemini-3.8-flash-medium` to
everything: the `gemini` skill ("by default the CLI picks"), the Tollbooth quota timer, any
`agy --print` a session runs. Scenario run from this session with a fake `agy` first in `PATH`:
`agy --print "/usage" --output-format json --mode plan < /dev/null` reached the binary as
`--model gemini-3.8-flash-medium --print /usage --output-format json --mode plan`.
Fix: in the headless branch pass the arguments through untouched (`command agy "$@"`) and let scripts
choose their model, which is what the decision intends; or guard the function with
`[[ $- == *i* ]] || return` is not enough (the tool's shell is non-interactive but still sources
the file), so the check has to be on the branch, not on the file. Update the DECISIONS entry either way.

### M2. `caffeine_toggle.sh` never keeps the screen awake: "ON" only swaps DPMS for the X screen saver
`polybar/.config/polybar/scripts/caffeine_toggle.sh:9-17`, `caffeine_status.sh:2`.
`toggle ON` runs `xset s 300; xset -dpms`, `toggle OFF` runs `xset s off; xset +dpms`, and the status
is "ON" whenever the screen-saver timeout is not 0. So the state called ON blanks the screen through
the X screen saver after 300 s, and the state called OFF blanks it through DPMS after 300 s
(`autostart.sh:15-17` sets `xset s off; xset +dpms; xset dpms 300 300 300`). Neither state keeps the
screen on, and the module's icon says the opposite of what the user expects. Live, read-only check
(`xset q` on `:0`): timeout 0, DPMS enabled with 300 s, status prints OFF; the first click would set
timeout 300 and DPMS off. (Xvfb ignores `xset s`, so the toggle was verified by reading the code and
the live query, not by running it on the private display.)
Fix: ON = `xset s off; xset -dpms` (nothing blanks), OFF = `xset s off; xset +dpms` (restore
autostart's DPMS), and status ON = `DPMS is Disabled` (`xset q | grep -q 'DPMS is Disabled'`).

### M3. One bad cached feed makes the mini calendar fail to open, silently, every time
`bin/.local/lib/mini-calendar/calevents.py:53-65,117-118`, `bin/.local/bin/mini-calendar:115,187-192`.
`refresh()` writes whatever a 200 answer contains into the cache without checking that it is iCal;
`events_between()` then calls `Calendar.from_ical()` with no error handling, and `refresh_view()` runs
in `__init__`, so the exception kills the window before it shows. `calendar-toggle` sends output to
`/dev/null`, so the click on the date simply does nothing, until someone deletes
`~/.cache/mini-calendar/calendar-N.ics`. Scenario: a cache file containing
`<html><body>Error 403</body></html>` -> `ValueError: Content line could not be parsed into parts`
from `events_between`. (A real 4xx is an `HTTPError`, which is caught; the case is a 200 with a
non-iCal body, or a feed truncated into something that still parses as text.)
Fix: in `refresh()` parse the download with `Calendar.from_ical` before `os.replace` and keep the
old file if it fails; in `events_between()` skip a cache file that does not parse (log it) instead
of raising.

### M4. `launch-bars.sh` waits forever for a polybar that does not die, and holds the lock while it waits
`polybar/.config/polybar/launch-bars.sh:7-8,14-16`.
`killall -q polybar` then `while pgrep -u "$UID" -x polybar; do sleep 0.1; done` with no limit. A
polybar that ignores SIGTERM (stopped, stuck in uninterruptible I/O, or a hung GL backend) keeps this
loop running; because the script took `flock 9` first, every later launch (each monitor event, each
`xmonad --restart`) queues behind it, so there are no bars at all until the process is killed by hand.
Scenario: fake `pgrep` that always exits 0 -> `timeout 4 launch-bars.sh` is killed at 4 s still
looping (exit 124). Fix: bound the wait (for example 30 x 0.1 s), then `killall -9 polybar` and go
on; use `flock -w 10 9` so a stuck launch does not block the next one.

## Low

### L1. `agy` asks for a model before `--help`, `--version`, `-h`
`bash/.bashrc.d/agy.sh:44-53`. Only subcommands and `-p/--print/--prompt` skip the question.
Scenario (pty, fake `agy`): `agy --help` printed the model menu first and then ran
`agy --model gemini-3.8-flash-medium --help`; `agy --version` likewise. Fix: add
`--help|-h|--version|-v` to the pass-through case.

### L2. The daily `agy models` refresh has no timeout and runs before the prompt
`bash/.bashrc.d/agy.sh:16-21`. When the cache is older than a day, the interactive `agy` first runs
`command agy models` (network); if that hangs (no DNS, captive portal) the terminal sits with no
output and nothing to press. Scenario: fake `agy models` that sleeps -> `_agy_pick_model` was
still waiting when killed after 5 s. Fix: `timeout 10 command agy models` (the stale list is kept on
failure already). Also `< "$cache" 2>/dev/null` (line 24) does not silence a missing file, because
the input redirection is opened first: with no cache file bash prints "No such file or directory"
on every launch (seen in the fake "space table" scenario). Put the loop in `if [ -r "$cache" ]`.

### L3. `agy.sh` is bash-only and breaks `sh` if sourced from it
`bash/.bashrc.d/agy.sh:22`. `local -a ids=() names=()` is a syntax error in dash: `sh -c ". agy.sh"`
fails with `Syntax error: "(" unexpected` and nothing after line 13 is defined. Fine as long as only
bash sources `~/.bashrc.d`; worth a guard (`[ -n "${BASH_VERSION:-}" ] || return 0`) because the
directory is shared.

### L4. `calendar-toggle` kills whatever process now has the saved pid
`bin/.local/bin/calendar-toggle:11-12`. The pid file is not removed when the calendar closes with
Esc or by `open_google`, and `kill -0` only checks that some process has that pid. Scenario: a pid
file pointing at an unrelated process of mine -> that process was killed. Fix: check the name before
killing (`[[ $(ps -o comm= -p "$pid") == mini-calendar ]]`), or drop the pid file and use
`pkill -x -u "$UID" mini-calendar`.

### L5. `phone`: `exit 1` inside `$(by_name ...)` only leaves the subshell
`bin/.local/bin/phone:14-19,34-37`. Scenario: `phone ring NoSuchPhone` printed "no device named",
then called gdbus with an empty device path, printed "ringing" and exited 0. Fix: capture the id
first (`id=$(by_name "$2") || exit 1`), then use it.

### L6. `autostart.sh` is run by `sh` (dash) and `source` is not a dash builtin
`xmonad/.xmonad/xmonad.hs:552`, `xmonad/.xmonad/autostart.sh:5`. `spawnOnce "sh /home/zeke/.xmonad/autostart.sh"`
runs it with dash on Ubuntu: `source ~/.xprofile` prints `sh: 1: source: not found` and the exports
are skipped (scenario run with a copy of the line). No visible effect here because
`/usr/sbin/lightdm-session` already loads `~/.xprofile` (the session's processes do have
`QT_QPA_PLATFORMTHEME`), but it would matter with `startx` or another display manager. Fix:
`. ~/.xprofile`, or spawn the script with its shebang (`spawnOnce "~/.xmonad/autostart.sh"`). The same
line hard-codes `/home/zeke`; `~/.xmonad/autostart.sh` works through `sh -c`.

### L7. `osd-brightness` on a machine with no backlight sends a broken notification
`bin/.local/bin/osd-brightness:10-28`. This desktop has no backlight device. Scenario: fake
`brightnessctl` that fails -> `(( pct >= 90 ))` with an empty `pct` is a bash syntax error, `icon` stays
unset, and `notify-send ... -h int:value: "Brightness" "%"` is sent. Fix: `pct=$(...) || exit 0` and
`[[ $pct =~ ^[0-9]+$ ]] || exit 0`.

### L8. `toggle-bar.sh second` works by substring accident
`polybar/.config/polybar/toggle-bar.sh:11`, `xmonad.hs:378`, `launch-bars.sh:39`. The bar is named
`secondary`; xmonad passes `second`; `pgrep -n -f "polybar second"` matches because it is a prefix.
Scenario: a process named `polybar secondary` was found by both `second` and `secondary`. Harmless
today; `pgrep -f "polybar main"` would also match any process whose command line contains that
text. Fix: pass `secondary` from xmonad.hs and match `-f "^polybar ${BAR}$"`, or use
`polybar-msg -p` with the pid saved by launch-bars.

### L9. `mini-calendar.ask_claude`: a whitespace-only answer raises `IndexError` in the worker thread
`bin/.local/bin/mini-calendar:290,314-318`. `(result or "No answer").strip().splitlines()[-1]` fails
when `result` is spaces or newlines only; `run_claude` catches `OSError, ValueError` only, so the
thread dies and the entry stays disabled with "Asking Claude..." until the window is closed.
Scenario: `"   \n"` -> `IndexError`. Fix: `lines = ...splitlines(); answer = lines[-1] if lines
else "No answer"` and catch `Exception` around `ask_claude` so the entry is always re-enabled.

## Checked and found fine

- Secrets: `~/.config/mini-calendar/ics-url`, `~/.config/printers.env`, `~/.config/ci-status/vm` and
  `~/.config/findajob/credentials` are mode 600; nothing in the repo or its history matches an iCal
  address, a GitHub token or a private key; the private LAN addresses in old versions of STATE.md,
  DECISIONS.md and setup-printers.sh are the ones DECISIONS 2026-10-06 chose to leave. `otp-to-clipboard`
  writes `last-otp` with umask 077 in the runtime dir; `ssh-askpass-rofi` prints the password to
  ssh's pipe only. `~/.cache/mini-calendar` is 777 and its feed file 666 (created once with umask 0; the
  session's umask is 0002), which the 750 home directory makes harmless; `calevents.refresh()` could
  still create the cache with `mode=0o700`.
- Stow: no two packages install the same path; `copyq/.stow-local-ignore` keeps `apply-theme.sh`
  out; everything outside `$HOME` is in `system/` with install notes. Only blemish: two `.pyc` files
